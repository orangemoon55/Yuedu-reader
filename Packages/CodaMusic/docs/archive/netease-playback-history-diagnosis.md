# 第三方播放未计入网易云历史：定位记录

日期：2026-10-27。

## 已确认的现象

用户确认：在 MeloX 与 Kumone 播放都不新增网易云历史；在网易云官方 App 播放后，新增记录也能在 MeloX 与 Kumone 看到。

这说明当前账号的远端历史读取链路能够工作，主要排查方向应转为**第三方播放事件的上报与服务端入账**，而不是先修改历史列表排序、分页或刷新 UI。

## 修复前实现与证据边界

Kumone 在开始播放时调用 PlaybackHistoryReporter.start，结束/切歌时调用 finish，分别发送 startplay 和 play。Reporter 会串行提交、绑定账号并在成功响应后触发历史失效刷新。MeloX 使用同类日志事件和上报路径。

修复前 K 请求：

```text
POST https://clientlog.music.163.com/eapi/feedback/weblog
eapi 签名路径：/api/feedback/weblog
主体：logs=<JSON 数组字符串>，header=<客户端/账号配置>，e_r=false
事件：startplay / play
```

K 只通过 HTTP 状态及顶层业务 code 判断请求是否成功。它没有在发送后确认目标歌曲是否进入远端历史。因此：

- 有上报调用，不代表用户设备上本次请求一定已发出。
- 返回 code=200，也不代表该事件一定被计入最近播放或听歌排行。
- 与 MeloX 源码一致，不能作为“历史记录功能线上可用”的验收证据。

定位阶段没有启动设备、执行自动化或使用账号发起新的上报。只读查询了本机最近两小时 playback-history 分类日志，没有取得可用条目；这不证明手机/iPad 上没有发送，也不能据此认定已收到 200。

## 上游已有相同类型问题

API Enhanced 的 [issue #167](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/issues/167) 记录了“听歌打卡返回 200/success，但播放次数不增加”的报告。

- 2026-06-10 的[单账号实测报告](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/issues/167#issuecomment-4666613213)提出 clientlog 域名 + eapi + osx + startplay/play 的方案；报告明确说明只验证单账号，不能保证普适或长期有效。
- 2026-06-19 的维护者回复称该方向被用于修复；2026-06-23 又有[失效反馈](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/issues/167#issuecomment-4779203757)。这些报告不能证明今天对所有账号均有效。
- 该项目在 2026-06-20 [加入 NCBL 上报实现](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/commit/83ee2cda34a20f64c6d343f7dfe22aa6a1c84b3d)。当前核对的提交为 `984cc021b8598cf94c22134f32a8426887fb2de7`。

新的 [scrobble_v1.js](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/984cc021b8598cf94c22134f32a8426887fb2de7/module/scrobble_v1.js) 与 [ncbl.js](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/984cc021b8598cf94c22134f32a8426887fb2de7/util/ncbl.js) 使用：

```text
POST https://clientlog3.music.163.com/api/clientlog/encrypt/upload?multiupload=true
multipart 文件上传，内容为 NCBL 加密日志
分开发送 _plv / _pld
包含客户端/设备/账号上下文，以及歌曲、音质、总时长和实际播放时长
```

其工具除 code=200 外还检查 data.successfiles 是否包含提交的文件名。这仍是日志接收确认，不能替代远端历史或统计变化的最终验证。

本地先前取得的网易云 Mac 3.1.8.3330 公开前端资源也能检索到 `_plv`、`_pld` 及 clientlog3 的 encrypt/upload 地址，与“存在另一套日志路径”相符；它不是本次手机官方 App 的抓包，不能据此宣称手机必然使用完全相同的传输。

## 模拟器实测结论（2026-10-28）

**已验证修复最近播放写入，累计听歌数也增加；周/累计排行的单曲次数尚未验证增加。**

先前 NCBL 候选实现存在两个实际失败点：

1. 当前网络下 `clientlog3.music.163.com` 在上传前发生 TLS 握手失败（`NSURLErrorDomain -1200`）。新增网易云 Mac 公开资源中也配置的第一方备用路由 `https://music.163.com/api/clientlog/encrypt/upload?multiupload=true`。仅对 TLS/连接建立失败重试同一文件；收到拒绝或连接中途断开时不盲目重传。保持 HTTPS 和证书校验，不修改用户网络设置。
2. 原候选采用上游的 gzip fallback。文件被 `successfiles` 接收，但实际历史未更新。改为有效 Zstandard 帧后，同一账号、同一首《可爱的家》可新增远端历史。说明文件回执不能证明日志已被解析入账；本次环境需要修正日志体格式。

不能从单账号结果推导“所有第三方被封”或“所有 gzip 永久失效”。本次修复依据是真实请求与远端读回的对照。

### 当前实现与验证

- NCBL v3 multipart `_plv/_pld`；Zstandard 原始块帧避免引入额外运行时。
- metadata 与 HTTP Cookie 使用一致的 PC 配置，token 保留原值，仅发往网易云第一方地址。
- 严格检查 `code` 及 `data.successfiles` 中的本次文件名。
- 事件绑定实际会话、账号、来源，保持串行次序；结束去重，零/非有限进度不产生时长事件。
- 使用真实歌曲 ID、时长、实际已知音质与 fee；不伪造会员、播放次数、UI referral 或音效。
- 收包后有限次数读取最近播放，以歌曲及新时间确认；区分 accepted / confirmed / unconfirmed。
- 23 项离线测试通过，涵盖独立 Node 24 Zstd/NCBL 样本、RFC 8439 ChaCha20 向量、TLS 备用路由、回执拒绝、会话次序、账号隔离及歌词请求。
- Swift 生成的 Zstd 帧经独立 Node 解码验证，覆盖 0、1、131072、131073、300000 字节。
- 最新模拟器与真机 Debug 构建均成功。模拟器实际页面已确认新历史及累计听歌数，并覆盖安装最终构建。iPhone 经 devicectl 安装成功；iPad 经 ios-deploy 返回 InstallComplete。本次均保留数据，安装后不启动真机应用或测试 Runner。

## iPhone 累计听歌数复查（2026-10-28 01:00 起）

用户反馈多首完整播完，最近播放更新但累计数不增。本次从连接的 iPhone 开发版容器只读取当前会话，再经网易云第一方接口读取统计；没有修改账号数据或通过探针补造播放事件。

- 01:01 账户详情 `listenSongs=23213`，最近记录已有 00:46–00:52 的新时间，确认这不是单纯最近列表读取失败。
- 以模拟器真实播放《小白船（哄睡版）》2619717044：01:05:29 开始，01:07:29 自然结束，两次文件上传均接收、最近记录确认。
- 01:07:58、01:08:37、01:09:28、01:10:11 直接读取累计数均仍为 23213；01:11:03 读取为 23215。此变化发生于下一首验证曲的结束事件之前，**不能归因于新补的码率字段**，也不能把每次完整播放等同于累计数必增 1。
- 修订版另以《鲨鱼一家》1847937175 做真实完整播放：01:09:54 `_plv` 接收；01:11:21 `_pld` 接收，实际记录 86 秒；最近播放确认。这证明当前修订版会发送自然结束时长事件，文件接收仍不能单独证明某首歌被计入累计数。
- iPhone 原运行时日志的只读收集需要本机管理员权限，本次未取得旧会话的 `_pld` 运行日志；未绕过此限制。因此不能断言用户过去每个会话的结束请求均已成功。

本次代码修正：

1. 最近播放确认后不再立即退出复查，继续在上报后的 3、15、45、120、180 秒失效刷新统计；不重复提交播放。
2. iPhone“我的”及账户详情统计的本地缓存从 1800 秒缩短为 60 秒，并先加载账户统计，再刷新收藏，避免收藏请求阻挡统计。
3. iOS 上报请求申请短时后台执行，降低自然结束停止音频后上报被系统挂起的风险；这属于补齐执行保障，未证实是用户这批播放的唯一原因。
4. 对在线播放补上接口返回的真实音源码率（桌面日志单位 kbps），未知时继续省略。日志区分 `_plv/_pld` 及真实秒数；不包含认证凭据。
5. 25 项上报/刷新/账号隔离测试通过，模拟器和真机构建通过。01:13 模拟器“我的”页自动显示 23215，与独立服务器读回一致，未手动增加页面数字。以上不能替代 iPhone 每个后续实际会话的计数验收。

## 线上验收标准

1. 对真实播放会话记录开始/结束事件是否进入提交队列、是否发送，以及脱敏后的 HTTP/业务响应；不得记录 MUSIC_U、CSRF 或完整加密请求。
2. 选一首不在当前最近列表中的实际播放歌曲，记录播放前远端历史和服务端时间；播放后按有限间隔读取目标歌曲是否新增或时间更新。
3. 先验证当前 clientlog/eapi 的实际结果，再按受控变量检查客户端配置或尝试 NCBL/PLV/PLD 契约；不要把换域名或改 UA 单独当成修复完成。
4. 最近播放与周/累计听歌排行分别验证：它们是两个读模型，不同事件和传播延迟可能不同。
5. 若需要应用内播放历史，可另设诚实标注的本地记录；本地插入不能作为“已同步网易云”的证明。
